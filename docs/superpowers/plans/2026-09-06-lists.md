# `/lists` — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** livrer `/lists` — la grille de cartes de liste avec sa mosaïque de quatre jaquettes, ses
trois gestes (créer, renommer, supprimer) — et le chemin qui la remplit depuis la fiche d'une œuvre.

**Architecture:** une lecture serveur unique porte les cartes, leurs décomptes et leurs jaquettes ;
cinq Server Actions écrivent, toutes par `authActionClient` et toutes gardées par la propriété de la
liste ; le rendu démarre entièrement dans le `_components/` de sa route.

**Tech Stack:** Next 16 (App Router, Server Components), Prisma 7 + `@prisma/adapter-pg`,
next-safe-action v8, Zod, shadcn/ui, Tailwind, Vitest.

**Spec:** [docs/superpowers/specs/2026-09-06-lists-design.md](../specs/2026-09-06-lists-design.md)

## ⚠️ Ce plan n'est pas exécutable d'une traite, et c'est voulu

La méthode du projet passe avant celle de la skill : **l'UI d'abord, la logique après validation,
et Alexis dicte la mise en page passe par passe.** Les quatre passes ci-dessous se terminent donc
chacune par un **point d'arrêt** — capture en 1440 et en 390, validation, puis seulement le commit.

Ce que ce plan fixe d'avance est ce qui est *décidé* : les signatures, les requêtes, les gardes, les
chemins de fichiers, le gel `knip`. Ce qu'il ne fixe pas est ce qui doit se voir avant d'être écrit :
l'espacement, les proportions de la mosaïque, la densité de la grille. **Un agent qui écrirait les
quatre passes sans montrer la première aurait manqué le point.**

## Global Constraints

Extraites de `CLAUDE.md` et `docs/ARCHITECTURE.md`. Elles valent pour **chaque** tâche.

- `src/app/` ne contient que du routing ; le métier vit dans `src/features/<domaine>/`.
- Un composant démarre dans le `_components/` de sa route ; promotion au **deuxième** appelant réel.
- `"use client"` sur la feuille interactive, jamais sur la page parente.
- `features/*/server/` est server-only : `import "server-only";` pour les lectures, `"use server"`

  `.metadata({ actionName })` puis `.inputSchema()`. **`.schema()` est l'API v7 et n'existe plus.**
- Aucune URL en dur : tout chemin par `src/config/routes.ts`.
- Jamais de `process.env.X` : `import { env } from "@/config/env"`.
- Base via `import { prisma } from "@/lib/db/prisma"`.
- Validation par Zod ; pas de `src/types/`, les types se dérivent par `z.infer`.
- Fichiers et dossiers en `kebab-case`. Pas de barrel `index.ts` dans `features/`.
- Un hook `PreToolUse` (`.claude/hooks/conventions-guard.mjs`) refuse les écritures qui violent

```ts
import { prisma } from "@/lib/db/prisma";
import { getSession } from "@/lib/auth/session";

async function currentUserId(): Promise<string> {
  const session = await getSession();
  if (!session) {
    throw new Error("Lecture de listes hors de la garde de `app/(app)/layout.tsx`.");
  }
  return session.user.id;
}

export async function getLists(): Promise<ListSummary[]> {
  const ownerId = await currentUserId();

  const rows = await prisma.list.findMany({
    where: { ownerId },
    orderBy: { updatedAt: "desc" },
    select: {
      id: true,
      title: true,
      description: true,
      _count: { select: { items: true } },
      items: {
        take: 4,
        orderBy: { rank: "asc" },
        select: {
          media: {
            select: { id: true, coverImage: true, titleRomaji: true, titleEnglish: true },
          },
        },
      },
    },
  });

  return rows.map((row) => ({
    id: row.id,
    title: row.title,
    description: row.description,
    itemCount: row._count.items,
    covers: row.items.map((item) => ({
      mediaId: item.media.id,
      cover: item.media.coverImage,
      title: item.media.titleRomaji ?? item.media.titleEnglish ?? "",
    })),
  }));
}
```

### Tâche 2.1 — les trois actions

**Files:**
- Create: `src/features/lists/server/lists.actions.ts`

**Interfaces:**
- Consomme : `createListSchema`, `updateListSchema`, `deleteListSchema`
  (`@/features/lists/schemas/lists.schema`) — **déjà écrits, ne pas les toucher** ;
  `authActionClient` ; `routes`.
- Produit : `createList`, `updateList`, `deleteList`.

- [ ] **Étape 1 : écrire les trois actions**

**Le point de sécurité de toute la branche : `ownerId` est dans le `where`, jamais dans une
vérification préalable.** Un `cuid` de liste vient du client ; le schéma en valide la *forme*, et
c'est le `where` de la mutation qui en valide la *propriété* — c'est écrit dans le docstring de
`lists.schema.ts`, et c'est ce qui empêche de renommer la liste d'un autre membre.

`updateMany` et `deleteMany` plutôt que `update` et `delete` : la variante au singulier lève quand
la ligne est absente, ce qui transformerait « pas ta liste » et « déjà supprimée » en erreur
serveur. La variante plurielle ne fait rien, ce qui est le bon résultat pour un geste dont le but
est que la ligne n'existe plus — même raisonnement que `removeEntry` dans `tracking.actions.ts`.

```ts
"use server";

import { revalidatePath } from "next/cache";

import { routes } from "@/config/routes";
import {
  createListSchema,
  deleteListSchema,
  updateListSchema,
} from "@/features/lists/schemas/lists.schema";
import { prisma } from "@/lib/db/prisma";
import { authActionClient } from "@/lib/safe-action";

export const createList = authActionClient
  .metadata({ actionName: "createList" })
  .inputSchema(createListSchema)
  .action(async ({ parsedInput, ctx }) => {
    const list = await prisma.list.create({
      data: {
        ownerId: ctx.user.id,
        title: parsedInput.title,
        description: parsedInput.description ?? null,
      },
      select: { id: true },
    });

    revalidatePath(routes.lists.root);
    return { id: list.id };
  });

export const updateList = authActionClient
  .metadata({ actionName: "updateList" })
  .inputSchema(updateListSchema)
  .action(async ({ parsedInput, ctx }) => {
    const { listId, title, description } = parsedInput;

    await prisma.list.updateMany({
      where: { id: listId, ownerId: ctx.user.id },
      data: { title, description: description ?? null },
    });

    revalidatePath(routes.lists.root);
    return { updated: true };
  });

export const deleteList = authActionClient
  .metadata({ actionName: "deleteList" })
  .inputSchema(deleteListSchema)
  .action(async ({ parsedInput, ctx }) => {
    await prisma.list.deleteMany({
      where: { id: parsedInput.listId, ownerId: ctx.user.id },
    });

    revalidatePath(routes.lists.root);
    return { deleted: true };
  });
```

- [ ] **Étape 1 : écrire les tests qui échouent**

```ts
describe("rankForAppend", () => {
  it("donne un premier rang quand la liste est vide", () => {
    expect(rankForAppend(null)).toBe("a0");
  });

  it("donne un rang qui suit le dernier", () => {
    const first = rankForAppend(null);
    const second = rankForAppend(first);
    expect(second > first).toBe(true);
  });

  it("n'a besoin que du dernier rang, pas de la liste", () => {

    const ranks = ["a0"];

    expect([...ranks].sort()).toEqual(ranks);
```

```ts
/**
 * Le rang d'une œuvre ajoutée **en fin de liste**.
 *
 * `generateKeyBetween(dernier, null)` : borne haute absente, donc aucune ligne existante n'est
 * touchée. C'est le pendant d'ajout de `rankAfterMove`, qui, lui, insère entre deux voisins.
 *
 * Elle ne reçoit que le dernier rang parce que c'est tout ce dont elle a besoin : l'action lit une
 * ligne (`orderBy: { rank: "desc" }, take: 1`) au lieu de rapatrier la liste entière pour en
 * regarder la fin.
 */
export function rankForAppend(lastRank: string | null): string {
  return generateKeyBetween(lastRank, null);
}
```

- [ ] **Étape 1 : écrire la lecture**

Une requête, pas deux : `items` est filtré sur ce `mediaId` seul, donc chaque liste rapporte zéro ou
une ligne, et `contains` s'en déduit. Lire toutes les listes puis toutes les appartenances
séparément coûterait un aller-retour de plus pour la même information.

```ts
export type ListMembership = { id: string; title: string; contains: boolean };

export async function getListMembership(mediaId: number): Promise<ListMembership[]> {
  const ownerId = await currentUserId();

  const rows = await prisma.list.findMany({
    where: { ownerId },
    orderBy: { updatedAt: "desc" },
    select: {
      id: true,
      title: true,
      items: { where: { mediaId }, select: { id: true }, take: 1 },
    },
  });

  return rows.map((row) => ({
    id: row.id,
    title: row.title,
    contains: row.items.length > 0,
  }));
}
```

### Tâche 3.3 — les deux actions de rangement

**Files:**
- Modify: `src/features/lists/server/lists.actions.ts`

**Interfaces:**
- Consomme : `addToListSchema`, `removeFromListSchema` (déjà écrits) ; `rankForAppend` (3.1) ;
  `ensureMediaMirror` (`@/features/media/server/media.mirror`).
- Produit : `addToList`, `removeFromList`.

- [ ] **Étape 1 : écrire les deux actions**

**Trois pièges, tous nommés par le brief, et tous dans ces trente lignes :**

1. **`ensureMediaMirror(mediaId)` avant l'écriture.** `ListItem.mediaId` porte une clé étrangère
   vers `Media` ; ranger une œuvre que personne n'a jamais croisée échouerait au niveau de la base.
   C'est exactement le piège que le suivi a rencontré.
2. **La propriété se vérifie ici, et elle ne peut pas passer par un `where` de `ListItem`** —
   celui-ci n'a pas d'`ownerId`. D'où la lecture de la liste d'abord, `where: { id, ownerId }` :
   sans elle, un `cuid` deviné laisserait écrire dans la liste d'un autre membre.
3. **`upsert` et non `create`.** `@@unique([listId, mediaId])` fait qu'un double clic, ou deux
   onglets, lèveraient sur la seconde insertion. `update: {}` rend le second geste inoffensif.

```ts
export const addToList = authActionClient
  .metadata({ actionName: "addToList" })
  .inputSchema(addToListSchema)
  .action(async ({ parsedInput, ctx }) => {
    const { listId, mediaId } = parsedInput;

    const list = await prisma.list.findFirst({
      where: { id: listId, ownerId: ctx.user.id },
      select: { id: true },
    });
    if (!list) throw new Error("Liste introuvable.");

    await ensureMediaMirror(mediaId);

    const last = await prisma.listItem.findFirst({
      where: { listId },
      orderBy: { rank: "desc" },
      select: { rank: true },
    });

    await prisma.listItem.upsert({
      where: { listId_mediaId: { listId, mediaId } },
      create: { listId, mediaId, rank: rankForAppend(last?.rank ?? null) },
      update: {},
    });

    revalidateLists(mediaId);
    return { added: true };
  });

export const removeFromList = authActionClient
  .metadata({ actionName: "removeFromList" })
  .inputSchema(removeFromListSchema)
  .action(async ({ parsedInput, ctx }) => {
    const { listId, mediaId } = parsedInput;

    /*
      La propriété passe par la relation plutôt que par une lecture préalable : `deleteMany` accepte
      un filtre sur `list`, donc une seule requête suffit — et sur une liste qui n'est pas la mienne,
      elle ne supprime rien plutôt que d'échouer.
    */
    await prisma.listItem.deleteMany({
      where: { listId, mediaId, list: { ownerId: ctx.user.id } },
    });
```
